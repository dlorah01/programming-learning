## 1. What a macro is, and when to reach for one

A **declarative macro** (`macro_rules!`) is a set of *pattern → template* rules that the compiler applies to **tokens**, before type checking. A call `name!(...)` is replaced by the template of the first rule whose pattern matches. The result must parse as an expression, statements, items, a pattern or a type, depending on where the call stands.

What a macro can do that a function cannot:

- take a **variable number** of arguments or an unusual syntax (`vec![1, 2, 3]`, `println!("{}", x)`);
- take arguments **lazily** (an argument that is not needed is never evaluated) ✓ (below);
- **generate items**: structs, enums, `impl` blocks for many types, tests;
- capture the **source text** of an expression (`stringify!`, as `assert!` does).

What it costs: harder errors, harder tooling (completion, debugging), longer compile times, and a second language to learn. Rule of thumb: use a **function** if you can, a **generic** or **trait** if you need to abstract over types ([Lesson 19](19_generics_and_bounds.md)), a `const fn` for compile-time values, and a macro only when the *syntax* or the *item generation* is the point.

A first, concrete difference ✓:

```rust
macro_rules! or_else { ($a:expr, $b:expr) => { match $a { Some(x) => x, None => $b } }; }
fn expensive() -> i32 { println!("expensive called"); 9 }
fn f(a: Option<i32>, b: i32) -> i32 { match a { Some(x) => x, None => b } }
fn main() {
    println!("{}", or_else!(Some(1), expensive()));
    println!("{}", f(Some(1), expensive()));
}
```

Output ✓: `1`, then `expensive called`, then `1`. The macro never evaluated `expensive()` because the `None` arm was not taken; the function call evaluated its argument first.

## 2. Anatomy of `macro_rules!`

```rust
macro_rules! hashmap {
    () => { ::std::collections::HashMap::new() };
    ($($k:expr => $v:expr),+ $(,)?) => {{
        let mut m = ::std::collections::HashMap::new();
        $( m.insert($k, $v); )+
        m
    }};
}

fn main() {
    let m = hashmap! { "a" => 1, "b" => 2, };
    let mut v: Vec<_> = m.iter().collect();
    v.sort();
    println!("{v:?}");
    let e: std::collections::HashMap<u8, u8> = hashmap!();
    println!("{}", e.len());
}
```

✓ Prints `[("a", 1), ("b", 2)]` and `0`.

- A macro is a list of **rules** separated by `;`. Each rule is `(matcher) => { transcriber }`. The delimiters around the matcher and transcriber can be any of `()`, `[]`, `{}` and do not matter.
- Rules are tried **in order**; the first one that matches wins. There is **no backtracking across fragments**: once a fragment such as `$e:expr` starts parsing, a parse error is a hard error, not "try the next rule" (see §2.2).
- `$name:fragment` binds a piece of the input. `$( ... ) sep rep` repeats: `rep` is `*` (0 or more), `+` (1 or more) or `?` (0 or 1), and `sep` is an optional separator token (`,`, `;`, `=>`, ...).
- In the transcriber, `$name` inserts the binding and `$( ... ) sep rep` repeats a group once per matched repetition. The variables inside must have been matched at the same repetition depth.
- The doubled braces `{{ ... }}` are intentional: the outer pair delimits the transcriber, the inner pair makes the expansion one **block expression**, so the `let` is local and the macro works in expression position.
- Use absolute paths (`::std::collections::HashMap`, and `$crate::...` in a library, §7) so the macro works wherever it is called.

### 2.1 Fragment specifiers

| Specifier | Matches | Notes |
|---|---|---|
| `expr` | an expression | stays a single **tree**: precedence is preserved ✓ (below) |
| `ident` | an identifier or keyword-like name | also matches raw identifiers; not `_` (from memory) |
| `ty` | a type | `Vec<u8>` ✓ |
| `pat` | a pattern (since edition 2021, top-level `|` allowed) | `Some(1 | 2)` ✓; `pat_param` excludes top-level `|` (from memory) |
| `stmt` | a statement without trailing `;` | from memory |
| `block` | a `{ ... }` block | ✓ |
| `item` | an item (fn, struct, impl, ...) | from memory |
| `path` | a path like `std::fmt::Debug` | from memory |
| `meta` | the inside of an attribute | used in `#[$m:meta]` ✓ |
| `vis` | a visibility (may be empty) | used in `$vis:vis` ✓ |
| `literal` | a literal, possibly negative | ✓ |
| `lifetime` | `'a` | from memory |
| `tt` | a single token **or** a delimited group `( ... )`, `[ ... ]`, `{ ... }` | the most flexible; ✓ |

A demonstration of several ✓:

```rust
macro_rules! show {
    (lit $l:literal) => { format!("literal {}", $l) };
    (id $i:ident) => { format!("ident {}", stringify!($i)) };
    (ty $t:ty) => { format!("type {}", stringify!($t)) };
    (pat $p:pat) => { format!("pat {}", stringify!($p)) };
    (blk $b:block) => { format!("block {}", $b) };
    (tt $t:tt) => { format!("tt {}", stringify!($t)) };
}
fn main() {
    println!("{}", show!(lit 5));
    println!("{}", show!(id foo));
    println!("{}", show!(ty Vec<u8>));
    println!("{}", show!(pat Some(1 | 2)));
    println!("{}", show!(blk { 1 + 1 }));
    println!("{}", show!(tt (a b)));
}
```

✓ Output: `literal 5`, `ident foo`, `type Vec<u8>`, `pat Some(1 | 2)`, `block 2`, `tt (a b)`.

**`expr` is not text substitution.** In C, `#define SQUARE(x) x * x` turns `SQUARE(2 + 3)` into `2 + 3 * 2 + 3`. A `$x:expr` fragment is parsed first and inserted as one node:

```rust
macro_rules! square { ($x:expr) => { $x * $x }; }
macro_rules! sq_tt { ($($x:tt)*) => { $($x)* * $($x)* }; }
fn main() {
    println!("{}", square!(2 + 3));
    println!("{}", sq_tt!(2 + 3));
}
```

✓ Prints `25` and then `11`. With `expr` the argument stays grouped; with raw `tt` repetition the tokens are pasted and precedence bites. (This does not make `expr` safe from *double evaluation*, §4.)

### 2.2 Ordering, ambiguity and the follow-set rule

Because there is no backtracking, put the **most specific rule first**:

```rust
macro_rules! m {
    ($e:expr) => { "expr" };
    ($i:ident) => { "ident" };
}
fn main() { println!("{}", m!(x)); }
```

✓ Prints `expr`: `x` is also a valid expression, so the second rule can never be reached. Swapping the order ✓ prints `ident` for `m!(x)` and `expr` for `m!(x + 1)`.

To keep patterns unambiguous, the language restricts what may **follow** a fragment. After `expr` (and `stmt`) only `=>`, `,` or `;` may follow:

```rust
// ERROR (no code)
macro_rules! bad { ($e:expr $t:ty) => { }; }
fn main() { }
```

✓ `error: `$e:expr` is followed by `$t:ty`, which is not allowed for `expr` fragments` with `= note: allowed there are: `=>`, `,` or `;``. Put a separator between them, or use `tt`.

When no rule matches you get a generic message ✓:

```rust
// ERROR (no code)
macro_rules! two { ($a:expr, $b:expr) => { $a + $b }; }
fn main() { println!("{}", two!(1)); }
```

`error: unexpected end of macro invocation`. A final catch-all rule using `compile_error!` makes this friendlier ✓:

```rust
// ERROR (no code)
macro_rules! need_two {
    ($a:expr, $b:expr) => { $a + $b };
    ($($t:tt)*) => { compile_error!("need_two! takes exactly two expressions") };
}
fn main() { println!("{}", need_two!(1, 2, 3)); }
```

✓ `error: need_two! takes exactly two expressions`.

## 3. Repetitions

Nested repetitions and the `$(,)?` trailing-comma idiom ✓:

```rust
macro_rules! table {
    ($($row:ident : [$($v:expr),* $(,)?]);* $(;)?) => {
        vec![ $( (stringify!($row), vec![$($v),*]) ),* ]
    };
}
macro_rules! opt {
    ($a:expr $(, $b:expr)?) => { $a $(+ $b)? };
}
fn main() {
    let t = table!(a: [1, 2, 3]; b: []; c: [4,]);
    println!("{t:?}");
    println!("{} {}", opt!(1), opt!(1, 2));
}
```

✓ Output: `[("a", [1, 2, 3]), ("b", []), ("c", [4])]` and `1 3`.

Rules to remember:

- A variable bound at depth *n* must be used at depth *n* in the transcriber (or inside a deeper repetition that iterates it).
- Two variables used in the same repetition must have been matched the same number of times.
- `$(...)?` cannot take a separator.
- The trailing-comma idiom `$(,)?` at the end of a list is a courtesy every list-like macro should offer.

Generating items is where macros earn their keep. One line per type ✓:

```rust
trait Describe { fn describe() -> &'static str; }
macro_rules! impl_describe {
    ($($t:ty => $s:literal),+ $(,)?) => {
        $( impl Describe for $t { fn describe() -> &'static str { $s } } )+
    };
}
impl_describe!(u8 => "byte", String => "string", Vec<i32> => "ints");
fn main() {
    println!("{} {} {}", u8::describe(), String::describe(), <Vec<i32>>::describe());
}
```

✓ Prints `byte string ints`. (The standard library does this for the integer types.)

## 4. Evaluation pitfalls

### 4.1 Double evaluation

A macro argument is *code to be pasted*, so using `$x` twice **evaluates it twice**:

```rust
macro_rules! max2 {
    ($a:expr, $b:expr) => {
        if $a > $b { $a } else { $b }
    };
}
fn main() {
    let mut n = 0;
    let mut next = || { n += 10; n };
    let m = max2!(next(), 5);
    println!("m = {m}");
    println!("calls = {}", n / 10);
}
```

✓ Prints `m = 20` and `calls = 2`: the condition used the first call (10 > 5) and the result used a *second* call. The usual fix is to bind once ✓ (prints `m = 10`, `calls = 1`):

```rust
macro_rules! max2 {
    ($a:expr, $b:expr) => {{
        let (a, b) = ($a, $b);
        if a > b { a } else { b }
    }};
}
fn main() {
    let mut n = 0;
    let mut next = || { n += 10; n };
    let m = max2!(next(), 5);
    println!("m = {m}");
    println!("calls = {}", n / 10);
}
```

(Binding makes arguments strict and in order; if you want laziness, as in `or_else!` above, keep the expression inside its branch.) Also remember that a binding inside the macro *moves* a non-`Copy` argument; take `&$x` if the macro should only borrow.

### 4.2 Statement versus expression position

A macro's expansion is parsed according to where it is called. A transcriber with a trailing semicolon or several statements is fine in statement position but not as an expression:

```rust
// ERROR (no code): trailing semicolon in expression position
macro_rules! v { () => { 1; 2 }; }
fn main() { let x = v!(); println!("{x}"); }
```

✓ Two errors: `macro expansion ignores `2` and any tokens following` and `trailing semicolon in macro used in expression position` (a deny-by-default future-compatibility lint, `semicolon_in_expressions_from_macros`). Wrap multi-statement expansions in `{{ ... }}` when you want a value.

Conversely, a macro that expands to `let a = 1; let b = 2;` works in statement position, but the bindings follow hygiene (§5) and unused-variable warnings point at the macro ✓ (`this warning originates in the macro `two_stmts``).

## 5. Hygiene

`macro_rules!` is **partially hygienic**. The rule of thumb:

- **Local variables, loop labels and `$crate`** are hygienic: a name introduced by the macro lives in the macro's own "syntax context" and cannot collide with, or be captured by, the caller's names (the technical term is *mixed-site hygiene*, from memory).
- **Everything else is not hygienic**: items (functions, types, statics, modules), fields, methods, other macros, generic parameters, and control-flow like `return`, `break` and `?`.

### 5.1 Locals

```rust
macro_rules! using_a {
    ($e:expr) => {{ let a = 42; $e }};
}
fn main() {
    let four = using_a!(a / 10);
    println!("{four}");
}
```

✗ `error[E0425]: cannot find value `a` in this scope`. The `a` inside the macro is not the `a` the caller wrote, so `$e` cannot see it. To let the caller name the variable, pass the identifier in ✓ (prints `4`):

```rust
macro_rules! using_a {
    ($a:ident, $e:expr) => {{ let $a = 42; $e }};
}
fn main() {
    let four = using_a!(a, a / 10);
    println!("{four}");
}
```

The protection works in the other direction too: a macro-internal temporary cannot capture the caller's variable of the same name ✓:

```rust
macro_rules! swap { ($a:expr, $b:expr) => {{ let tmp = $a; $a = $b; $b = tmp; }}; }
fn main() {
    let mut tmp = 1;
    let mut y = 2;
    swap!(tmp, y);
    println!("{tmp} {y}");
}
```

✓ Prints `2 1`. In a C-style textual macro the macro's `tmp` would shadow the caller's `tmp` and break the swap.

A macro that declares a variable for the caller must take its name as an `ident` ✓:

```rust
macro_rules! decl { ($n:ident, $v:expr) => { let $n = $v; }; }
macro_rules! decl_hidden { ($v:expr) => { let hidden = $v; }; }
fn main() {
    decl!(x, 5);
    println!("{x}");
    decl_hidden!(6);
    println!("{hidden}");
}
```

✗ `error[E0425]: cannot find value `hidden` in this scope` (`this error originates in the macro `decl_hidden``); `decl!(x, 5)` works.

### 5.2 Labels, `return`, `self`

Loop labels are hygienic ✓: a macro using `'outer` inside does not clash with the caller's `'outer`:

```rust
macro_rules! find_first_even {
    ($v:expr) => {{
        let mut found = None;
        'outer: for x in $v { if x % 2 == 0 { found = Some(x); break 'outer; } }
        found
    }};
}
fn early(v: Vec<i32>) -> i32 {
    macro_rules! must { ($o:expr) => { match $o { Some(x) => x, None => return -1 } }; }
    let a = must!(v.first().copied());
    a + 100
}
fn main() {
    'outer: for _ in 0..1 {
        println!("{:?}", find_first_even!(vec![1, 3, 4, 5]));
        break 'outer;
    }
    println!("{} {}", early(vec![]), early(vec![1]));
}
```

✓ Prints `Some(4)` and `-1 101`. And `return` is **not** hygienic: `must!` returns from the *calling function* (`early(vec![])` gave `-1`). That is how `?`-like macros such as `ensure!` in the practical challenge work, and it is also a surprise for readers: a macro call can contain an invisible early return.

`self` is a keyword, but a macro defined *outside* a method cannot name the method's `self` ✓:

```rust
// ERROR E0424
macro_rules! get { () => { self.x }; }
struct S { x: i32 }
impl S { fn f(&self) -> i32 { get!() } }
fn main() { println!("{}", S { x: 1 }.f()); }
```

✓ `error[E0424]: expected value, found module `self``. Defined *inside* the method, or taking `self` as an `$s:ident`/`expr` argument, it works (✓ the inside-the-method version printed `1`).

### 5.3 Items are not hygienic

```rust
macro_rules! make_fn {
    ($name:ident) => { fn $name() -> &'static str { stringify!($name) } };
}
make_fn!(hello);
macro_rules! call_helper { () => { helper() }; }
fn helper() -> i32 { 7 }
fn main() { println!("{} {}", hello(), call_helper!()); }
```

✓ Prints `hello 7`. Two consequences: macro-generated items are visible to the whole module (so two macros generating the same fn name collide), and a macro that refers to a free function `helper()` finds *whatever `helper` is in scope at the call site*, which may be a different function, or none. In library macros, refer to your own items by `$crate::path` and to std by absolute `::std`/`::core` paths (§7).

### 5.4 Forwarded fragments are opaque

Passing an `expr` (or `ty`, `pat`, ...) fragment on to another macro turns it into one opaque node that the inner macro can only match with the same fragment kind, not with literal tokens. `ident`, `lifetime` and `tt` stay transparent ✓:

```rust
macro_rules! inner { (a) => { "a" }; ($($t:tt)*) => { "other" }; }
macro_rules! outer_tt { ($($t:tt)*) => { inner!($($t)*) }; }
macro_rules! outer_ident { ($i:ident) => { inner!($i) }; }
macro_rules! outer_expr { ($e:expr) => { inner!($e) }; }
fn main() {
    println!("{} {} {}", outer_tt!(a), outer_ident!(a), outer_expr!(a));
}
```

✓ Prints `a a other`. If a later rule must look *inside* the tokens (a "tt muncher", §6), take `tt`s, not `expr`.

## 6. Recursion, internal rules and tt-munchers

A macro may call itself. A classic example counts tokens:

```rust
macro_rules! count {
    () => { 0usize };
    ($head:tt $($tail:tt)*) => { 1usize + count!($($tail)*) };
}
fn main() {
    println!("{}", count!(a b c d e));
    const N: usize = count!(x y z);
    let arr = [0u8; N];
    println!("{}", arr.len());
}
```

✓ Prints `5` and `3`. But the expansion depth is limited. With 250 tokens ✓:

```text
error: recursion limit reached while expanding `count!`
  = help: consider increasing the recursion limit by adding a `#![recursion_limit = "256"]` attribute to your crate
```

(the default limit is 128, from memory; the compiler's suggested value was ✓ 256). Raising the limit is a workaround; better to avoid linear recursion. The crate in §14 counts token trees **without recursion**, by building an array of `()` and taking its length:

```rust
macro_rules! replace_unit { ($_t:tt) => { () }; }
macro_rules! count {
    () => { 0usize };
    ($($t:tt)+) => { <[()]>::len(&[$(replace_unit!($t)),+]) };
}
fn main() {
    const N: usize = count!(a b c d);
    println!("{N} {}", count!());
}
```

✓ Prints `4 0`, and it is a constant expression. The crate's test counts 150 tokens (more than the recursion limit) ✓.

**Internal rules and accumulators.** A rule starting with a marker token like `@acc` is a private helper entry. Together with recursion on `tt`s this is the *tt-muncher* pattern: consume the head of the input, carry state in extra arguments, recurse on the rest ✓:

```rust
macro_rules! calc {
    (@acc $acc:expr;) => { $acc };
    (@acc $acc:expr; plus $n:literal $($rest:tt)*) => { calc!(@acc ($acc + $n); $($rest)*) };
    (@acc $acc:expr; times $n:literal $($rest:tt)*) => { calc!(@acc ($acc * $n); $($rest)*) };
    ($start:literal $($rest:tt)*) => { calc!(@acc $start; $($rest)*) };
}
fn main() {
    println!("{}", calc!(2 plus 3 times 4));
}
```

✓ Prints `20` (left to right: `(2 + 3) * 4`). It is a tiny DSL, built from patterns alone. Munchers cost compile time quadratically in the worst case (every step re-parses the remainder, from memory), so keep inputs small and prefer a proc macro (Lesson 35) for big grammars.

## 7. Scope, export and `$crate`

**Textual scope.** A `macro_rules!` macro is usable only *after* its definition in source order, within the module (and child modules) where it is defined ✓:

```rust
// ERROR (no code)
fn main() { println!("{}", late!()); }
macro_rules! late { () => { 1 }; }
```

✓ `error: cannot find macro `late` in this scope` (plus an `unused_macros` warning for the definition). The scope does not leave a module on its own ✓: a macro defined inside `mod m` is not visible after `mod m { ... }` ends (`error: cannot find macro `only_in_m` in this scope`, with `help: have you added the `#[macro_use]` on the module/import?`).

**Two ways to share a macro**:

1. *Within a crate*: `pub(crate) use name;` right after the definition turns the macro into a normal path-importable item ✓:

   ```rust
   mod util {
       macro_rules! twice { ($e:expr) => { 2 * $e }; }
       pub(crate) use twice;
   }
   use util::twice;
   mod other { pub fn f() -> i32 { crate::twice!(4) } }
   fn main() { println!("{} {}", twice!(3), other::f()); }
   ```

   ✓ Prints `6 8`. (`#[macro_use]` on a `mod` is the older mechanism that extends textual scope past the module's end; from memory.)

2. *Across crates*: `#[macro_export]` places the macro at the **root of its crate** (`maclab::map!`), regardless of the module it was written in (from memory; the crate in §14 defines them at the root). The caller imports it like any item: `use maclab::map;`.

**`$crate`.** Inside an exported macro, `$crate` expands to the defining crate's root, whatever the caller named it or imported. Use it for your own items (`$crate::Failed`, `$crate::__private::HashMap`), and use `::core::...` / `::std::...` for the standard library, so a caller who has their own `Result`, `Some` or `HashMap` in scope cannot break the expansion. The test `macros_use_absolute_paths` in §14 shadows `Result`, `Some`, `HashMap` and `from` and still passes ✓.

**Semver.** An exported macro's *patterns* are public API. Adding a rule is usually fine, but making an existing pattern stop matching, or changing what an existing call expands to in a way that changes types or evaluation order, can break callers ([Lesson 33](33_modules_api_design_rustdoc.md)). Helper macros that callers must be able to reach but should not use get `#[doc(hidden)]` and a `__` prefix (the crate's `__replace_unit!`); as Lesson 33 stressed, `#[doc(hidden)]` is not privacy.

## 8. Debugging macros

1. **Read the error's origin.** Messages say `this error originates in the macro `name`` ✓. The note continues with `-Z macro-backtrace` (nightly only, not run) to show the expansion chain.
2. **See the expansion**: `cargo expand` (an external tool, not installed here) or `cargo rustc -- -Zunpretty=expanded` (nightly). Without either, test the macro on tiny inputs and use `stringify!`.
3. **`stringify!` and `concat!`** build text at compile time ✓:

   ```rust
   macro_rules! show { ($e:expr) => { println!("{} = {:?}", stringify!($e), $e) }; }
   fn main() {
       show!(1 + 2 * 3);
       show!(vec![1, 2].len());
       println!("{}", concat!("a", 1, 2.5, true));
   }
   ```

   ✓ Output: `1 + 2 * 3 = 7`, `vec![1, 2].len() = 2`, `a12.5true`.
4. **`compile_error!`** in a catch-all rule (§2.2) turns "no rules expected the token" into your own message. A `compile_fail` doctest can pin that a macro rejects bad input, but macros give no `E0xxx` code, so (unlike Lesson 33's contracts) it can only be a plain `compile_fail`; make sure the example fails for the reason you intend.
5. **Test the macro like a function**: call it with edge cases (empty, one item, trailing comma, side effects, shadowed names), as the practical challenge does.

## 9. Common mistakes

1. **Evaluating an argument twice** (§4.1). Bind to a local first.
2. **Pasting `tt`s where you meant an expression**, losing precedence (§2.1).
3. **Rule order**: general rule first, so specific rules are unreachable (§2.2).
4. **Relying on a local variable the macro introduces** (§5.1): pass the name as `$x:ident`.
5. **Hidden control flow**: `return`, `break` and `?` inside a macro affect the caller (§5.2); document it.
6. **Unqualified paths in exported macros**: `HashMap::new()` breaks when the caller has no import or a different `HashMap`. Use `$crate` or `::std`.
7. **Forgetting `{{ }}`** so that a `let` or several statements leak or fail in expression position (§4.2).
8. **Using a macro where a generic function works.** Prefer the function: better errors, better tooling.
9. **Deep recursion** (§6). Prefer repetition and non-recursive tricks.
10. **No trailing-comma rule** `$(,)?`, which annoys users with rustfmt-style multi-line calls.
11. **Changing an exported macro's accepted syntax** without a semver bump.
12. **Testing only the happy path.** Macro bugs live at the syntax corners.

## 10. Performance, reliability, security

- **Run time.** A macro expands before code generation, so the *expanded* code has the cost of ordinary code. A macro is not faster than a function; it is only inlined by construction. (A function would often be inlined too.)
- **Compile time and code size.** Expansion happens for every call site and is re-parsed and type-checked each time. Huge generated impl sets (one `impl` per type per trait) and tt-munchers grow build time; I have not measured it here, so take it as a design warning, not a number. If many monomorphized copies are the issue, move the logic into a generic function and keep the macro thin.
- **Reliability.** A macro's behavior is part of its caller's code: hidden returns, double evaluation and non-hygienic items are all reliability hazards. Keep expansions small, bind arguments once, use absolute paths, and test with hostile inputs.
- **Security.** `macro_rules!` runs no code of its own at compile time: it only rewrites tokens (procedural macros are different; Lesson 35). The risk is in what it *generates*: a macro that expands to `unsafe { ... }` hides the `unsafe` from the call site, so every use inherits the safety obligation without showing it. Prefer macros that generate *safe* code, put `unsafe` blocks inside documented functions, and never build SQL, shell commands or paths by pasting tokens from untrusted data (macros only see source tokens, not run-time values, but a macro that wraps `format!` into a command string recreates injection bugs). Rust does not guarantee a macro-generated program is secure; it only checks that the expansion type-checks and obeys the borrow rules.

1. **(Warm-up)** Name three things a `macro_rules!` macro can do that a function cannot.
2. **(Warm-up)** Why does `square!(2 + 3)` print `25` with `$x:expr` but `11` when written with `tt` repetition?
3. **(Easy)** Why is `macro_rules! bad { ($e:expr $t:ty) => {}; }` rejected, and how do you fix it?
4. **(Medium)** Write `strings!["a", "b"]` that expands to a `Vec<String>`; allow a trailing comma and an empty list.
5. **(Medium)** Write `min_of!(a, b, c, ...)` that evaluates every argument exactly once.
6. **(Medium-hard)** Write `with_getters!` that declares a struct and, for each field, a method of the same name returning a reference.
7. **(Hard)** Why does the recursive `count!` fail for 250 tokens, and how can you count without recursion?
8. **(Hard)** `macro_rules! m { () => { let x = 1; }; } fn main() { m!(); println!("{x}"); }` fails. Explain and give two fixes.

<details markdown="1">
<summary>Answers</summary>

1. Take a variable number of arguments or custom syntax (`vec![]`); evaluate arguments lazily or capture their source text (`assert!`, `stringify!`) ✓; generate items such as structs and `impl` blocks; contain early `return`/`break` that affect the caller.
2. `$x:expr` is parsed as one expression node and inserted as a unit, so `$x * $x` is `(2 + 3) * (2 + 3)` ✓ `25`. Pasting `tt`s gives the token stream `2 + 3 * 2 + 3` ✓ `11`. (It is still double evaluation if the argument has side effects.)
3. `expr` fragments may only be followed by `=>`, `,` or `;` (✓ error text), so that the parser knows where the expression ends. Add a separator: `($e:expr, $t:ty)`, or take `tt`s.
4. ```rust
   macro_rules! strings {
       () => { ::std::vec::Vec::<::std::string::String>::new() };
       ($($s:expr),+ $(,)?) => { ::std::vec![$(::std::string::String::from($s)),+] };
   }
   fn main() {
       let v = strings!["a", "b",];
       let e = strings!();
       println!("{v:?} {}", e.len());
   }
   ```
5. ```rust
   macro_rules! min_of {
       ($x:expr $(,)?) => { $x };
       ($x:expr, $($rest:expr),+ $(,)?) => {{
           let first = $x;
           let rest = min_of!($($rest),+);
           if first <= rest { first } else { rest }
       }};
   }
   fn main() { println!("{}", min_of!(4, 2, 9)); }
   ```
   The `let`s evaluate each argument once, left to right (compare `max_of!` in §14 ✓).
6. ```rust
   macro_rules! with_getters {
       (
           $(#[$m:meta])*
           $vis:vis struct $name:ident { $($fvis:vis $f:ident : $t:ty),* $(,)? }
       ) => {
           $(#[$m])* $vis struct $name { $($fvis $f: $t),* }
           impl $name { $( pub fn $f(&self) -> &$t { &self.$f } )* }
       };
   }
   with_getters! {
       #[derive(Debug)]
       pub struct Point { x: i32, y: i32 }
   }
   fn main() {
       let p = Point { x: 1, y: 2 };
       println!("{} {} {p:?}", p.x(), p.y());
   }
   ```
   Fields and methods live in different namespaces, so the same identifier works for both.
7. Each `count!` call expands to another `count!` call, one per token, and the compiler stops at its recursion limit (✓ error with a suggested `#![recursion_limit = "256"]`). Count without recursion by mapping every token to `()` and taking the length of the array (✓ §6): `<[()]>::len(&[$(replace_unit!($t)),+])`.
8. Hygiene (✓ §5.1): the `x` declared inside the macro lives in the macro's syntax context, so `println!("{x}")` cannot see it (`E0425`). Fix 1: pass the name in (`macro_rules! m { ($n:ident) => { let $n = 1; }; }`, `m!(x);`). Fix 2: make the macro an expression that returns the value (`macro_rules! m { () => { 1 }; }`, `let x = m!();`).

</details>

## 12. Debugging challenge

A helper macro should return the larger of a sensor reading and a threshold. In a test with a counter standing in for the sensor, it returns 20, not the 10 that the single reading produced, and the sensor was read twice.

```rust
macro_rules! max2 {
    ($a:expr, $b:expr) => {
        if $a > $b { $a } else { $b }
    };
}
fn main() {
    let mut n = 0;
    let mut next = || { n += 10; n };
    let m = max2!(next(), 5);
    println!("m = {m}");
    println!("calls = {}", n / 10);
}
```

✓ It prints `m = 20` and `calls = 2`. Explain why, and fix it so that `calls = 1`.

<details markdown="1">
<summary>Solution</summary>

A `$a:expr` fragment is *code*, not a value. Each time `$a` appears in the transcriber, the expression is pasted again and evaluated again: once in the condition (`10 > 5`) and once in the `then` branch, which produced `20`. The expression `next()` has a side effect, so the two evaluations disagree, and the macro returns a value that no single call produced. (With a pure expression the bug is invisible, which is why it survives review; it becomes a real bug with I/O, counters, `iter.next()`, or just expensive calls.)

The fix is to evaluate each argument once into a local and then compare (✓ `m = 10`, `calls = 1`). The locals are hygienic, so their names cannot collide with the caller's variables:

```rust
macro_rules! max2 {
    ($a:expr, $b:expr) => {{
        let (a, b) = ($a, $b);
        if a > b { a } else { b }
    }};
}
```

Note the double braces (a block expression) and that the arguments are now evaluated eagerly and in order. The library's `max_of!` uses the same pattern and a test (`max_of_picks_the_largest_and_evaluates_once`) counts the calls; mutation M4 below replaces the bindings with repeated `$x` and that test fails.

</details>

## 13. Interview questions

1. What is the difference between a `macro_rules!` macro and a function?
2. What does "hygiene" mean in Rust macros, and what is *not* hygienic?
3. Why can a macro evaluate its argument twice, and how do you prevent it?
4. What is `$crate` for?
5. What is a tt-muncher, and what are its costs?
6. What is the macro recursion limit and how can you avoid hitting it?
7. How do you share a `macro_rules!` macro within a crate and across crates?
8. When would you choose a procedural macro (or a generic function) over `macro_rules!`?

<details markdown="1">
<summary>Answers</summary>

1. A macro rewrites tokens at compile time before type checking: it can take arbitrary syntax and a variable number of arguments, evaluate arguments lazily (✓ `or_else!`), generate items, and contain control flow that affects the caller. A function is type-checked, has fixed arity and evaluates its arguments first.
2. Names introduced by a macro (local variables, labels, `$crate`) cannot clash with the caller's names (✓ `swap!` with a caller's `tmp`; ✓ the `a`/`hidden` errors). Items, fields, methods, other macros and `return`/`break`/`?` are not hygienic (✓ `hello()` and `call_helper!()`, ✓ early `return -1`).
3. `$x:expr` is pasted wherever `$x` appears, so using it twice evaluates it twice (✓ `m = 20`, `calls = 2`). Bind it to a local with `let` once, inside a block.
4. In an exported macro it names the defining crate's root regardless of how the caller imports it, so the expansion can refer to your own items (`$crate::Failed`, ✓ in `ensure!`) even when the caller has not imported them.
5. A recursive macro that consumes one token tree per step and carries state in accumulator arguments (✓ `calc!`). Costs: recursion limit (✓ 250 tokens failed), poor error messages and compile time that grows with input size (quadratic in the worst case; from memory).
6. The default is 128 (from memory; ✓ the error suggests raising it with `#![recursion_limit = "256"]`). Avoid by iterating with repetitions instead of recursion, or by non-recursive tricks like the array-length count (✓ 150 tokens in tests), or by raising the limit.
7. Within a crate: `pub(crate) use name;` after the definition (✓), or textual scope / `#[macro_use]` (from memory). Across crates: `#[macro_export]`, which puts it at the crate root, and callers `use crate_name::name;`.
8. A proc macro when you need to inspect or generate code from real Rust syntax (derives, attribute macros, parsing a complex grammar, good error spans). A generic function or trait when you only need to abstract over types or values, which gives much better errors and tooling.

</details>

## 14. Practical challenge: `maclab`

Build a library crate `maclab` of declarative macros. Requirements:

1. `count!`: count token trees; non-recursive; usable in `const` and array lengths; works beyond the recursion limit.
2. `map!`: `HashMap` literal. `map!()` is empty; trailing comma allowed; later duplicates win; capacity hint from `count!`; each key and value expression evaluated once, in order.
3. `max_of!`: maximum of 1 or more expressions; each evaluated exactly once; trailing comma allowed.
4. `ensure!`: `ensure!(cond)` returns `Err(Failed(<cond text>))` from the enclosing function; `ensure!(cond, err)` returns `Err(err.into())`. The error type `Failed` implements `Error`.

//! `maclab`: a small library of declarative macros, written to show the
//! habits that make `macro_rules!` macros robust.
//!
//! * [`count!`]: count token trees without recursion (usable in `const`).
//! * [`map!`]: build a `HashMap` literal.
//! * [`max_of!`]: maximum of several expressions, each evaluated once.
//! * [`ensure!`]: return early with an error unless a condition holds.
//! * [`swap!`]: swap two places (a hygiene example).
//! * [`string_enum!`]: an enum with `as_str`, `Display`, `FromStr` and `ALL`.
//! * [`id_type!`]: a typed `Copy` identifier newtype.
//!
//! Every macro that expands to paths uses `$crate::...` or absolute `::core`
//! / `::std` paths, so it works however the caller has imported (or shadowed)
//! names.
//!
//! ```
//! use maclab::{map, max_of};
//! let m = map! { "a" => 1, "b" => 2 };
//! assert_eq!(max_of!(m["a"], m["b"], 0), 2);
//! ```
//!
//! A wrong invocation is a compile error with a readable message (macros
//! cannot carry an `E0xxxx` code, so this doctest can only be a plain
//! `compile_fail`):
//!
//! ```compile_fail
//! let _ = maclab::map! { "a" => 1, "b" };
//! ```

#![deny(missing_docs)]

use std::fmt;

#[doc(hidden)]
pub mod __private {
    //! Re-exports used by the macros. Not part of the public API.
    pub use std::collections::HashMap;
}

/// Replaces any one token tree with `()`. Used by [`count!`].
#[doc(hidden)]
#[macro_export]
macro_rules! __replace_unit {
    ($_t:tt) => {
        ()
    };
}

/// Counts the **token trees** it is given (a `,` is one token tree, and so is
/// a whole parenthesised group). The result is a `usize` constant expression.
///
/// Unlike the textbook recursive `1 + count!(...)`, this expands to the length
/// of an array of `()`, so it never hits the macro recursion limit.
///
/// ```
/// const N: usize = maclab::count!(a b c d);
/// assert_eq!(N, 4);
/// assert_eq!(maclab::count!(), 0);
/// assert_eq!(maclab::count!((a b) [c]), 2);
/// ```
#[macro_export]
macro_rules! count {
    () => {
        0usize
    };
    ($($t:tt)+) => {
        <[()]>::len(&[$($crate::__replace_unit!($t)),+])
    };
}

/// Builds a [`HashMap`](std::collections::HashMap) from `key => value` pairs.
/// A trailing comma is allowed; later duplicates overwrite earlier ones. With
/// no arguments it is an empty map (the types are inferred).
///
/// ```
/// let m = maclab::map! { "one" => 1, "two" => 2, };
/// assert_eq!(m["two"], 2);
/// let e: std::collections::HashMap<u8, u8> = maclab::map!();
/// assert!(e.is_empty());
/// ```
#[macro_export]
macro_rules! map {
    () => {
        $crate::__private::HashMap::new()
    };
    ($($k:expr => $v:expr),+ $(,)?) => {{
        let mut m = $crate::__private::HashMap::with_capacity($crate::count!($($k)+));
        $( m.insert($k, $v); )+
        m
    }};
}

/// The largest of one or more expressions. Each expression is evaluated
/// exactly once, in order, which a naive `if $a > $b { $a } else { $b }`
/// would not do.
///
/// ```
/// assert_eq!(maclab::max_of!(3, 9, 4), 9);
/// assert_eq!(maclab::max_of!("x"), "x");
/// ```
#[macro_export]
macro_rules! max_of {
    ($x:expr $(,)?) => {
        $x
    };
    ($x:expr, $($rest:expr),+ $(,)?) => {{
        let first = $x;
        let rest = $crate::max_of!($($rest),+);
        if first >= rest { first } else { rest }
    }};
}

/// The error produced by [`ensure!`] when no custom error is given. It holds
/// the text of the failed condition.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Failed(pub &'static str);

impl fmt::Display for Failed {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "condition failed: {}", self.0)
    }
}

impl std::error::Error for Failed {}

/// Returns `Err(error.into())` from the **enclosing function** unless the
/// condition holds. With one argument the error is [`Failed`] holding the
/// condition's source text.
///
/// ```
/// use maclab::{ensure, Failed};
/// fn half(n: u32) -> Result<u32, Failed> {
///     ensure!(n % 2 == 0);
///     Ok(n / 2)
/// }
/// assert_eq!(half(8), Ok(4));
/// assert_eq!(half(7), Err(Failed("n % 2 == 0")));
/// ```
#[macro_export]
macro_rules! ensure {
    ($cond:expr $(,)?) => {
        $crate::ensure!($cond, $crate::Failed(::core::stringify!($cond)))
    };
    ($cond:expr, $err:expr $(,)?) => {
        if !$cond {
            return ::core::result::Result::Err(::core::convert::From::from($err));
        }
    };
}

/// Swaps two places using a temporary. The temporary is hygienic, so a caller
/// variable named `tmp` is not captured.
///
/// ```
/// let (mut tmp, mut other) = (1, 2);
/// maclab::swap!(tmp, other);
/// assert_eq!((tmp, other), (2, 1));
/// ```
#[macro_export]
macro_rules! swap {
    ($a:expr, $b:expr) => {{
        let tmp = $a;
        $a = $b;
        $b = tmp;
    }};
}

/// The error returned by the `FromStr` impl that [`string_enum!`] generates.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ParseEnumError {
    /// The name of the enum that was being parsed.
    pub type_name: &'static str,
    /// The rejected input.
    pub input: String,
}

impl fmt::Display for ParseEnumError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        write!(f, "unknown {}: {:?}", self.type_name, self.input)
    }
}

impl std::error::Error for ParseEnumError {}

/// Declares a fieldless enum together with `ALL`, `as_str`, `Display` and
/// `FromStr`, from one list of `Variant => "text"` pairs. Attributes and
/// visibility are passed through.
///
/// ```
/// maclab::string_enum! {
///     /// Traffic light.
///     #[derive(Debug, Clone, Copy, PartialEq)]
///     pub enum Light { Red => "red", Green => "green" }
/// }
/// assert_eq!("red".parse::<Light>(), Ok(Light::Red));
/// assert_eq!(Light::Green.to_string(), "green");
/// assert_eq!(Light::ALL.len(), 2);
/// assert!("blue".parse::<Light>().is_err());
/// ```
#[macro_export]
macro_rules! string_enum {
    (
        $(#[$meta:meta])*
        $vis:vis enum $name:ident { $($variant:ident => $text:literal),+ $(,)? }
    ) => {
        $(#[$meta])*
        $vis enum $name { $($variant),+ }

        impl $name {
            /// Every variant, in declaration order.
            pub const ALL: &'static [$name] = &[$($name::$variant),+];

            /// The text this variant is parsed from and displayed as.
            pub fn as_str(&self) -> &'static str {
                match self { $($name::$variant => $text),+ }
            }
        }

        impl ::core::fmt::Display for $name {
            fn fmt(&self, f: &mut ::core::fmt::Formatter<'_>) -> ::core::fmt::Result {
                f.write_str(self.as_str())
            }
        }

        impl ::core::str::FromStr for $name {
            type Err = $crate::ParseEnumError;
            fn from_str(s: &str) -> ::core::result::Result<Self, Self::Err> {
                match s {
                    $($text => ::core::result::Result::Ok($name::$variant),)+
                    other => ::core::result::Result::Err($crate::ParseEnumError {
                        type_name: ::core::stringify!($name),
                        input: ::std::string::ToString::to_string(other),
                    }),
                }
            }
        }
    };
}

/// Declares a `Copy` identifier newtype over an integer-like type, with
/// `new`, `get`, `From<inner>`, `Display` and the usual derives.
///
/// ```
/// maclab::id_type! { pub struct UserId(u64); }
/// let id = UserId::new(7);
/// assert_eq!(id.get(), 7);
/// assert_eq!(UserId::from(7), id);
/// assert_eq!(id.to_string(), "7");
/// ```
#[macro_export]
macro_rules! id_type {
    ($(#[$meta:meta])* $vis:vis struct $name:ident($inner:ty);) => {
        $(#[$meta])*
        #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)]
        $vis struct $name($inner);

        impl $name {
            /// Wraps a raw value.
            pub const fn new(raw: $inner) -> Self {
                $name(raw)
            }
            /// The raw value.
            pub const fn get(self) -> $inner {
                self.0
            }
        }

        impl ::core::convert::From<$inner> for $name {
            fn from(raw: $inner) -> Self {
                $name(raw)
            }
        }

        impl ::core::fmt::Display for $name {
            fn fmt(&self, f: &mut ::core::fmt::Formatter<'_>) -> ::core::fmt::Result {
                ::core::fmt::Display::fmt(&self.0, f)
            }
        }
    };
}

    swap!(a, b);
    v[0] = a;
    v[1] = b;
    assert_eq!(v, [20, 10]);
}

string_enum! {
    /// A test enum.
    #[derive(Debug, Clone, Copy, PartialEq, Eq)]
    pub enum Level { Debug => "debug", Info => "info", Warn => "warn", }
}

#[test]
fn string_enum_round_trips_and_reports_errors() {
    assert_eq!(Level::ALL, &[Level::Debug, Level::Info, Level::Warn]);
    for l in Level::ALL {
        assert_eq!(l.as_str().parse::<Level>(), Ok(*l));
        assert_eq!(l.to_string(), l.as_str());
    }
    let err = "loud".parse::<Level>().unwrap_err();
    assert_eq!(
        err,
        ParseEnumError {
            type_name: "Level",
            input: "loud".to_string()
        }
    );
    assert_eq!(err.to_string(), "unknown Level: \"loud\"");
    assert!("".parse::<Level>().is_err());
    assert!(
        "Info".parse::<Level>().is_err(),
        "matching is case-sensitive"
    );
}

id_type! {

**Design notes.**

- `count!` maps every token tree to `()` through the hidden helper `__replace_unit!` and takes the slice length, so there is no recursion and the result is a constant expression. It counts *token trees*: a comma counts, a parenthesised group counts once (tested).
- `map!` passes `$($k)+` to `count!`: each `$k:expr` is a single opaque tree, so the count equals the number of keys, and the keys are not evaluated there because `__replace_unit!` throws its argument away.
- `max_of!` is recursive but only as deep as the argument count; each level binds its `$x` once. `ensure!(cond)` forwards to its two-argument rule and builds the error with `stringify!`; both rules keep `$cond` as one `expr`, so `ensure!(a || b)` is not mis-parsed (tested).
- `ensure!` and `swap!` rely on hygiene differently: `swap!` needs the local `tmp` to be invisible to the caller; `ensure!` deliberately uses non-hygienic `return`.
- Paths: `$crate::__private::HashMap`, `$crate::Failed`, `$crate::ParseEnumError` for the crate's items and `::core::...` / `::std::...` for the standard library; the shadowing test would fail if any bare `Result` or `Some` leaked into an expansion.
- Not handled: no `no_std` support (`map!` and `string_enum!` use `std`), no `BTreeMap` variant, `count!` counts trees rather than parsing item boundaries, `id_type!` does not accept generics, and I did not fuzz macro inputs. Macro hygiene around `$crate` and `#[macro_export]` across crates was exercised only through this crate's own integration tests and doctests.

## 15. Key takeaways

- A `macro_rules!` macro rewrites tokens by the first matching rule; there is no backtracking across fragments, so order rules from specific to general (✓ `expr` first made the `ident` rule unreachable).
- `$x:expr` keeps its structure (✓ `25`), `tt` pasting does not (✓ `11`), and an `expr` argument is code that is evaluated every time you paste it (✓ `calls = 2`): bind it once.
- Hygiene covers local variables, labels and `$crate`; it does not cover items, fields, methods or control flow (✓ `E0425` for macro-introduced locals, ✓ early `return -1`, ✓ `hello()`).
- Prefer repetition to recursion (✓ recursion limit at 250 tokens, ✓ the `()`-array count handles 150 and more).
- Exported macros: `#[macro_export]`, `$crate` and absolute paths; inside a crate `pub(crate) use` (✓). Their syntax is semver-relevant API.
- Debug with `stringify!`, `compile_error!` catch-all rules and small tests; expansion viewers are nightly or external tools (not run here).
- Use a function or generic first. A macro that expands to `unsafe` or hides a `return` makes the call site misleading; Rust does not make macro-generated code secure.

**Connections.** [Lesson 33](33_modules_api_design_rustdoc.md)'s visibility and re-export rules decide how macros are shared (`pub(crate) use`, `#[doc(hidden)]`) and how their syntax becomes API; [Lesson 26](26_error_design.md)'s error design is behind `Failed` and `ParseEnumError`; [Lesson 19](19_generics_and_bounds.md)'s generics are the alternative for type abstraction; [Lesson 15](15_newtype_typestate.md)'s newtypes are what `id_type!` stamps out.
